📝 总体评估

📋 总体评估

项目概况：zcode-advisor 是 ZCode（z.ai 桌面版，Electron/Claude Code 同构）的插件：一个独立配置的审查副模型，每轮对话结束时被动审查转录增量，产出 nit/concern/blocker 三级建议并注回会话。约 5100 行 JavaScript（零第三方依赖），含三个交付形态：插件本体（hooks/commands）、角标外挂（CDP 注入）、发行包（NSIS setup.exe + macOS DMG）。已发布 v0.2.1，192 项测试。

主要风险：本次审计发现 2 个 blocker，其中「同步清单漏 tools/」会让插件 MCP 完全失效、「插件启用状态丢失」使用户现场跑的是空转版本——两者都已在审计中修复并验证。更结构性的是四层部署缓存（源 → 副本 → 宿主市场缓存 → 宿主 cache）曾三次导致「改了代码却装出旧版本」，现已用同步脚本 + 守卫测试 + 自动化链路封堵。

亮点：① 零第三方依赖贯彻彻底（自研 ZIP/TAR/ICO/ICNS，字节结构经系统工具交叉校验）；② 故障有界设计扎实——advisory-only 纪律 + 37 处空 catch 均为「绝不拖垮主会话」的有意取舍，且有测试锁定；③ 注释质量高：多数解释「为什么」并记录实测教训（如「诚实说明」类注释）；④ 测试真实性强——e2e 用真实子进程覆盖三事件与快照契约，守卫测试在本次审计中当场抓到同步漂移。

优先修复：① 拆分 advisor-hook.js（874 行 / 20 函数，SRP 违反）；② 消除 normalizeChatEndpoint 与 readHistory 的重复实现；③ 给 ocr-review.sh 加并发锁（实测 4 个进程堆叠）；④ 补 hooks 侧可观测性（当前 0 处日志）；⑤ DOM 桩升级（无法暴露类名选择器错误，UI 改动依赖真机验证）。

总评：A（8.0）——工程纪律明显高于同类个人项目：零依赖、故障有界、注释如实、测试用真实子进程。本次发现的 blocker 属「部署链路」而非「代码质量」，且已修复。剩余问题集中在可维护性（单文件过长、两处重复实现）与工程配套（无并发锁、无 hooks 日志、DOM 桩有盲区），均可增量改进，不阻塞发布。

A2. 异步/同步审查超时余量过小 —— 实为「重试各自起算」

判定：成立，但根因不是「余量 30s 太小」。callReviewer 内部的 429/5xx 退避重试本就共享 deadline，真正的问题是外层：reviewTurn 的「空响应重试」每次调用 callReviewer 都各自起算 Date.now() + timeoutMs。

修复
callReviewer 接受调用方传入的 deadline；reviewTurn 整轮生成一次 deadline 写入 reviewParams，空响应重试复用同一对象；重试前加预算守卫（剩余 <10s 直接放弃）
